I tried to build a "token optimization stack" for coding agents. Here's why I killed it.

A pilot benchmark, a $5.60 receipt, and the 97%-savings number that turned out to be a silent failure.

How it started

This started from a plain, unglamorous problem: I kept running into token limits at work. I was using Claude Code for real engineering work, burning through context and budget faster than I wanted to, and the obvious next question was — can I actually cut that down without cutting into the quality of what the agent produces? Not "use a cheaper model and hope," but something more deliberate: a stack of tools that each attack a different part of the token bill — how much context gets read, how much gets re-read, how verbose the agent's own output is, how it navigates a codebase in the first place.

That question turned into a side project: token-optimization-stack, a public repo documenting a composable set of tools meant to sit around Claude Code and reduce token spend, plus token-stack-benchmarks, a benchmarking harness to actually measure whether any of it worked.

I'm writing this up because the project ended, a few weeks in, in a place I didn't expect: not with a validated stack and a savings number, but with a concrete demonstration that the token-savings numbers I was looking at were actively misleading, and a cost model that made the whole exercise stop making sense before I even got to publish a result. I think both of those are more useful to write about than a clean win would have been.

What the stack looked like early on

The first version of the stack had five tools in it:

  • Graphify — turns a codebase into a queryable knowledge graph, so the agent can ask "what calls this" instead of grepping and reading files to find out.
  • Serena — symbol-level code navigation and editing via LSP, instead of raw file reads and text edits.
  • Headroom — advertised as transparent context compression that "requires no behavioral changes" once installed.
  • LiteLLM — a routing layer, with the idea being complexity-based model routing: cheap model for simple subtasks, expensive model only when needed.
  • Caveman — output-side compression; a terser interaction style plus compressed subagent output, to cut down on verbose back-and-forth.

Two of those five didn't survive contact with an actual benchmark harness.

Headroom turned out not to do what its own documentation implied. The only registration path that didn't involve wrapping the whole claude invocation in a separate launcher (headroom init claude) registers an on-demand MCP tool — something the agent can call, not something that transparently compresses context whether the agent calls it or not. headroom doctor confirmed nothing was actually being routed through it without a separately running proxy process and an ANTHROPIC_BASE_URL override — a materially heavier integration than "requires no behavioral changes" suggested. On top of that, its mcp serve subcommand crashed outright against a current MCP SDK install, needing an old, pinned mcp<2 dependency to even start.

LiteLLM had a more fundamental problem: its usage-based routing is a load-balancing strategy across provider endpoints, not the complexity-based, per-subtask routing the idea in my head required. And Claude Code, mechanically, sends one fixed model for an entire -p session — there's no hook to swap models mid-task based on subtask complexity. The tool I wanted didn't exist yet in the shape I needed it.

Both got removed rather than kept in as unverified claims. What was left — Graphify, Serena, a context-compression/caching layer (LeanCTX), and Caveman — became the actual stack under test.

Why I had to stop

I want to be honest about the actual reason this stopped, because it's not "the idea was wrong" (that came later) — it's that the experiment itself stopped being economically sane to keep running.

The benchmarking methodology I'd written called for real rigor: SWE-bench Verified and Multi-SWE-bench tasks (real GitHub issues with a known-good fix and a real test suite to check it against, not synthetic problems), sixteen repos, twenty tasks per repo, five ablation arms to attribute savings to each individual tool, three repeats per task per arm because a single LLM run is an anecdote, not a measurement. That's the "full matrix." Multiply it out and it's on the order of 4,800 individual agent runs — each one a full Claude Code session against a real repo, inside a fresh Docker container, potentially spinning up a Java language server, cloning dependencies, compiling.

I never got anywhere near that. I ran a deliberately cheap 2-task-per-repo pilot — 31 tasks, 2 arms (baseline vs. full stack), one repeat — specifically to sanity-check the idea before spending real money on the full matrix. Even that pilot, run on the cheapest model I had (claude-haiku-4-5, medium effort — not Sonnet, not Opus), partially completed (11 of 31 task pairs, 22 of 62 planned runs) at roughly $5.60 in raw agent API cost alone. That's before counting EC2 compute, the local Docker image builds, or the many hours of environment debugging it took just to get a single task to run at all — getting a Linux-shaped benchmark harness working cleanly on both an EC2 box and an Apple Silicon Mac turned into its own multi-day project, full of failures that had nothing to do with the actual research question.

Extrapolate that per-run cost across the actual full matrix — 4,800 runs instead of 22 — and you're looking at somewhere north of $1,200 in API spend, on the cheapest model available, before a single result is trustworthy enough to publish. And that number assumes haiku is good enough to trust for this task. It wasn't:

  • On the Java-track tasks, the agent produced zero correct fixes under the full stack. Some of that was real stack-caused breakage, but some of it was haiku simply giving up or producing a patch that only deleted its own scratch debug file.
  • On the tasks it did solve at baseline, the full stack broke two out of three of them under the "improvements" — one task where the agent stopped producing any code change at all, one where it produced a plausible-looking patch that didn't actually fix the bug.

That's the tension that killed this specific approach to the project: the model cheap enough to make the benchmark affordable was not reliably good enough to distinguish "the stack is helping" from "the stack is confusing a weak model." Stepping up to a stronger model to fix that would have multiplied an already uncomfortable cost estimate by several times more, for a side project.

Is this savings number — or this correctness failure — actually about the stack? Or is it about the fact that I'm running everything on the cheapest model I could afford to run 4,800 times of?

I didn't have a good answer to that. I still don't. That ambiguity, at that price, is where I stopped.

What I actually found, for what it's worth

Even the partial pilot data was worth publishing, because it directly contradicts what a token-savings-only view would have told me. On the three Python-track tasks the plain baseline agent solved correctly, adding the full optimization stack:

  • Broke one of them completely — the agent, under the "optimized" stack, produced no code change at all. Looked at from the token-savings side alone, this run showed 97% fewer tokens used — the single best-looking number in the whole pilot. It was also a complete failure to do the task.
  • Broke a second one — a patch was produced, it applied, and the target test still failed.
  • Left the third one correct, but using more tokens than baseline, not fewer.

Net result on the tasks that mattered: the full stack preserved correctness on 1 of 3 previously-working fixes, and even that one case was a net loss on cost. If I'd stopped at the token-count dashboard — which is what most "token optimization" claims I'd seen elsewhere seem to do — I would have shipped a blog post with a 97% savings headline number pulled from the exact run that silently failed the task.

Token and cost savings numbers, without a real correctness check against the actual test suite, aren't just incomplete — they can point in exactly the wrong direction. And the biggest, flashiest savings number is a plausible place for that to happen, not an unlikely one.

If you want to pick this up

I'm not going to keep running this — not because I think the underlying question is answered, but because I can't afford to answer it properly on my own budget with the current tooling. If someone wants to take this further, both repos are public:

  • token-optimization-stack — the stack itself: setup scripts and docs for Graphify, Serena, LeanCTX, and Caveman, plus the benchmarking methodology this whole pilot followed.
  • token-stack-benchmarks — the harness: Dockerized ablation-arm runner, task sampling, and the SWE-bench / Multi-SWE-bench scoring scripts, including everything I found along the way getting a Linux-shaped benchmark harness to run correctly on both EC2 and an Apple Silicon Mac — case-sensitivity bugs, architecture mismatches, a brand-new Python version breaking a scoring dependency, and more.

Contributions, forks, and "actually here's why your pilot was wrong" pull requests are genuinely welcome. A few concrete open threads if you want a starting point:

  • Why does the full stack produce empty or broken patches on tasks the plain baseline solves correctly? Not yet root-caused. Could be the compression layer dropping context the agent actually needed, could be something else entirely.
  • The full 5-arm ablation was never run — only a 2-arm baseline-vs-full-stack pilot. It's entirely possible one specific tool in the stack is responsible for the regression and the others are fine, or even helping.
  • Nobody has run this on a stronger model. Everything above is haiku at medium effort, specifically because it was the only model cheap enough to pilot at all. It's an open question whether Sonnet or Opus, at real per-run cost, would show a real positive effect that a weak model can't demonstrate — I just couldn't afford to find out.
